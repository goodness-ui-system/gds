1. Introduction — how to read this document

This white paper is the design system explained. It is a living document: every example in it is rendered by the system itself from the same style tokens the applications use, so when a token changes, every example on this page changes with it — nothing here is a screenshot.

Each chapter follows the same rhythm: the question in plain language, the options that exist, the live example right after the words that describe it, the trade-offs, the recommendation, and a status marker saying whether the matter is decided or still open. Terms of art are defined in ordinary words the first time they appear.

Until a selection pass happens, this document is a catalog of candidates, not a verdict: wherever several ways of doing the same thing exist, every credible option is shown side by side so the final system can be chosen by looking at real examples. A companion file, the specimen, renders the same catalog with no text at all — a pure visual reference — and the two evolve in parallel: any change to an example is made in both places.

The switches in the top-right corner work on this whole document: the palette family, the light theme, and the density scale re-point the same design tokens applications switch with server-rendered attributes. There is no JavaScript on this page.

2. Color — the palette families and the shared contract

Every color in the system lives in one file of named values called tokens (a token is a named design decision, like --color-text, that components reference instead of raw values). Tokens come in three tiers: primitives (the raw palette below), semantic aliases (names that describe a job, like text or danger), and component references. Components may only use the middle tier — which is what makes whole-system reskinning a one-file change.

Three palette families exist — warm, cool, and mono — and a contract guarantees they are interchangeable: every family defines exactly the same named steps (fourteen neutrals and four accent steps), enforced by an automated check. A product picks a family the way it picks a typeface; nothing else in the system needs to know.

Primitives (tier 1) of the active family. Components never touch these directly — they consume the semantic aliases. The family switch (top right) replaces this palette entirely; only one family is ever on screen.

3. Dark and light as equals — and the halation problem

The system treats dark and light as two equal renderings of the same design, not a main theme and an afterthought. The operating system's preference leads (via the standard prefers-color-scheme signal), and a stored per-user choice overrides it. Every color pair is contrast-solved independently in both themes and verified by an automated checker against the WCAG accessibility floors (WCAG is the international standard for readable contrast).

Dark mode has a trap of its own called halation: pure white text on a dark background scatters in the eye and appears to glow, with a halo around each letter — especially for readers with astigmatism. The published evidence converges on the fix: dark-theme text is never pure white but a light gray in the #DEDEDE–#EBEBEB band, and the canvas is never pure black. Those ceilings are enforced by the same checker that enforces the contrast floors — flip the Light theme switch above and note that both renderings hold.

The appearance control — how a person switches

System-first theming needs a visible control, and the control has a settled shape: one button in the header opens a small menu with exactly three choices — System, Light, Dark. The active choice is checked, and the System row tells the reader what it resolves to right now ("Match device — currently Dark"), so nobody picks System blind and discovers the result afterward. Every option is visible before anything is clicked; the reader selects an outcome instead of guessing.

The obvious-seeming alternative — a single icon that cycles through the three modes on each click — is rejected, because a cycling control must answer two different questions with one symbol: "what mode am I in?" and "what happens if I click?" No icon can say both at once, so the reader always has to click and watch to find out — the exact confusion the control exists to remove.

The trigger itself offers two candidate styles. The sun/moon glyph reports the current appearance honestly — a sun when the page is light, a moon when it is dark — while the menu handles the choosing, so the two jobs never collide. The contrast circle (◐) is the neutral alternative: it says "appearance" without picking a side — less informative, but state-agnostic. Both render below; the sun/moon in this document follows the Light switch above.

The menu, with the resolves-to line under System — on this page that line is driven purely by a stylesheet media query reading the device preference, no script:

One question stays open: how long an override lasts. Session-scoped memory treats the device setting as the source of truth — a one-time choice never hijacks future visits, and the site greets every session in System. A stored per-user choice, rendered by the server so the page never flashes the wrong theme, respects a person who has decided once and means it. The first suits public sites; the second suits the signed-in working applications this system targets. Both remain on the table.

Recommendation: the three-option menu with the resolves-to line, always opening in System; sun/moon as the default trigger; the cycling toggle never. Persistence — session-scoped vs. stored per user — is the pending decision, and may legitimately differ between public sites and signed-in applications.

4. Typography — sans for interface, mono for meaning

Two typefaces, each with a job. The sans-serif face carries the interface: labels, body text, headings, in a small fixed ramp of sizes so every screen uses the same few steps. The monospaced face is reserved for values that carry meaning in their exact characters — identifiers, timestamps, amounts, counts — where aligned digits and unmistakable characters earn their keep. Type never wears decoration; hierarchy comes from size and weight, not color.

5. Density — one axis, three steps

Density is how much information fits on a screen before it stops being comfortable. In this system density is a setting, not a redesign: three named steps on one axis, switched by a single attribute. Tight packs the most rows per screen for heavy data review (28px controls); normal is the default reading rhythm (34px); loose adds air for touch use, presentations, and long reading sessions (40px). Two options would assume one kind of user; three cover the spectrum while staying finite.

The switch changes only the rhythm of repeated things — control heights, table rows, menu and panel rows. Text sizes, section padding, and page structure do not move, so switching density never feels like zooming. Every step keeps click targets at or above the 24px accessibility floor. Try it: the Density control in the header re-flows every example in this document.

Adopted as principle

8. Selection controls — the choice family

A working screen asks its reader to choose all day: which rows, which columns, which interval, on or off. Behind every one of those moments sit just two questions, and together they decide which control belongs there. First, what shape is the choice — one of a set, many of a set, or a single yes/no? Second, when does it take effect — immediately, or only when a form is saved? Each control in this family is one cell of that grid; drift happens when a control is picked for its looks instead of its cell.

Checkbox, drawing option A — native (browser-drawn, accent-color)

The checkbox is the many-of-a-set control, and also the single opt-in ("include archived"), and it always means: collected now, applied when the form is saved. Two ways of drawing it are on display. Option A lets the browser draw the box and only tints it with the accent token — one line of style, and specialized displays (high-contrast modes, print) handle it natively because nothing was overridden.

Checkbox, drawing option B — custom-drawn, with the mixed state

Option B draws the box from the system's own tokens: identical in every browser, and every state — including the mixed state — styled deliberately. The mixed state (the dash) belongs to a parent checkbox standing over a partly-selected set, familiar from the select-all box in a table header: some rows checked, not all. It is a visual state the server renders as a class, and an honest limitation comes with it: the web platform offers no script-free way to announce "partly checked" to assistive technology, and bolting the announcement on with an attribute is forbidden on a native checkbox — so where the mixed reading matters, the honest control is a server-rendered select-all button instead. The cost of option B in general is responsibility: what the browser guaranteed for free, the drawn control must re-earn, which is why both options stay on display rather than one being assumed better.

Radio, drawing option A — native · drawing option B — custom-drawn

The radio button is the one-of-a-set control: choosing one releases the others, which is exactly what it should signal that a checkbox does not. The same two drawing options apply. Radios earn their place when every option deserves to be seen before choosing — a handful of visible answers beats a dropdown that hides them behind a click. Stack them vertically when they stand alone in a form; one option per line scans faster than a row.

The radio carries a genuine standing debate: should one option come pre-selected? One school says always — a pre-selected group can never be submitted empty, and people overwhelmingly keep defaults, so the common case is fast. The other says never — a preselected answer gets submitted unread, becoming false data, and once any radio is picked the group cannot be un-picked, so a mistaken click has no way back to "no answer". Most of the war dissolves on a distinction: a settings screen re-rendering the saved value is displaying state, not preselecting — every school accepts it. The debate only truly applies to first-time questions, and there the resolution is by consequence: preselect a safe, honest default where one exists (an interval, a sort order — never merely the first option); start empty when the answer is itself data and no default is defensible, give the list an honest escape option ("None of these"), and let required-field validation catch the skip.

Switch — md · sm · disabled (immediate effect; never beside a Save button)

The switch is the on/off control with one extra promise: the effect happens the moment it flips, like a light switch. That promise is the entire difference from a checkbox — same state, different tense. From it follows the rule that a switch never sits in a form that ends in a Save button: a control that promises "now" inside a container that means "later" misleads twice at once. In this system the switch is a checkbox carrying the switch role — current screen readers announce a true switch, and the failure mode is a correctly-stated checkbox — plus HTML's own emerging switch attribute for browsers that know it natively; the checked state stays native, never restated in an attribute. It is styled as a track and thumb. Its label always names the thing being turned on, never the current state; a separate state word beside the control is a permitted variant where research shows confusion.

Switch rows — the settings-list presentation

Settings screens give the switch its natural home: a row per setting, title and explanation on the left, the switch on the right edge where the thumb expects it, each row one hairline apart. The whole row is the click target.

The anti-pattern — state words inside the track (shown to be rejected)

Writing ON and OFF inside the track is rejected. The words cannot answer their own question — does the word describe the state the switch is in, or the state it will go to? — different products have meant both, so the reader must flip it to find out. And words baked into a control break the moment the interface is translated: the track cannot grow with the language. Position and fill already say everything; the label beside the control says what is being switched.

Segmented control, option A — raised segment · option B — tinted accent · with counts

The segmented control is a radio group in button clothing: one-of-few, every option visible, in a single compact bar. It earns its place in toolbars and dashboards where a labeled radio list would be too tall — picking an interval, a scope, a facet of the data. The discipline: it changes a value or a filter, never the screen — switching between whole views is the job of tabs, and dressing one as the other teaches readers the wrong reflex. Two to five segments; past five, the bar stops being scannable and a dropdown takes over. Underneath it is made of real radio inputs, so keyboard and assistive behavior come from the browser, not from script. Two skins are on display — the raised segment, quiet and structural; the tinted accent, louder about which value is active — and a variant with mono counts, for when the numbers themselves inform the choice.

Toggle button — pressed state via aria-pressed · labeled · icon-only pair

The toggle button is a button that stays pressed — on/off wearing a button's clothes, for places where the action is the point: watch this view, bold this text. Its state lives in the pressed attribute, rendered by the server, and the pressed look must never be color alone — fill and border change together, so the difference survives grayscale and color-blindness. One discipline keeps it honest: the label never changes with the state — the same word stays put ("Watch", pressed or not) and the pressed state carries the answer, because a control that changes its word and its state at once leaves the reader unsure which one it just announced. Icon-only toggles carry a known ambiguity (does a filled star mean "starred" or "press to star"?), which is why the labeled form is preferred wherever space allows.

Choice chips — many-of-many as compact pills (a checkbox group in chip clothing)

Choice chips are a checkbox group in chip clothing: many-of-many, horizontal, compact — the filter facets above a table. Each chip is a real checkbox under a pill face; selecting one adds a check mark alongside the fill change, so the state never rests on color alone. They differ from the removable chip of chapter 9, which displays an already-applied value: the choice chip is the act of choosing itself.

Option tiles — a radio dressed as a small card, for choices that need a description

When each option needs a sentence of explanation — a plan, a sync mode — a bare radio label runs out of room. The option tile gives each choice a small card: title, description, and a visible radio dot, because a bordered card alone does not read as "pick one of these". One rule keeps tiles honest: nothing else interactive lives inside one — a link or button nested in a choice makes two targets fight for one click.

The whole family folds into one decision path. On/off that acts now: switch. On/off collected by a form: checkbox. One of up to about five, in a form: radios, stacked; in a toolbar: a segmented control. One of many: the dropdown select, the control of last resort once options stop fitting on screen. Many of a set, in a form: a checkbox list; above a table: choice chips. A choice whose options need explaining: option tiles. An action that stays on: a toggle button. Recommendation: adopt the family with this decision path, and pick one drawing option — native or drawn — for checkbox and radio rather than shipping both.

11. Sections, not cards

The default layout unit for working screens is the full-bleed section: blocks that touch, sharing a single hairline separator. Two cards cost the eye three elements between two pieces of content (edge, gap, edge); two sections cost one. The result is calmer, denser screens where separation is information, not decoration.

Cards are not forbidden — they are scoped. Independent, glanceable content earns a card: executive dashboards, widget grids, control environments. The duality is deliberate and documented, so the choice is always an argument, never a habit.

12. Navigation — sidebar, tabs, menu

Navigation is the sections-not-cards rule turned sideways: the sidebar is a flat rail on the page background, separated from content by one vertical hairline, with the current item as the only filled shape. Overlays — dropdown menus, dialogs, palettes — are the legitimate exception: something that floats above other content needs an edge and a shadow to read as a separate layer. Navigation rows also run tighter than data rows, because a menu item is targeted, not read.

The sidebar is not a card. It is a flat rail sitting directly on the page background, separated from the content by a single vertical hairline — the same sections-not-cards rule, turned sideways. Only the current item gets a filled pill; everything else is plain text.

The side menu — anatomy

The rail's principle is settled; its anatomy still holds open choices, and each one below is shown as options to pick from. The questions: how a group announces itself, how the items are written, whether they carry icons and at what size, how the current item is marked, what separates one run of items from the next, and how a group folds.

The group label. The small heading above a group of items comes in two styles. The uppercase eyebrow, letterspaced and muted, reads unmistakably as furniture — nobody tries to click it. The sentence-case label is quieter and closer to the items' own voice, and it carries the readability argument: all-capitals text is measurably slower to read because word shapes disappear, which is why several major systems ban it. Either way the label is static text, never a link — and if uppercase is chosen, the transform lives in the stylesheet, never typed into the content, so the style can change later without touching a word.

Submenus. Two candidates fold a group of children under a parent. Always-open shows everything: children sit indented under a connector line, nothing is ever hidden, and the cost is a longer rail. Collapsible puts the children behind the parent row: the native disclosure element supplies the open-and-close behavior with no script at all, the chevron sits at the row's end pointing right when closed and turning down when open — the prevailing convention, though timed testing mildly favors a leading chevron for its constant click position — and the whole row is the toggle target, never just the icon. The server can render frequently-used groups already open, and a third route exists that needs no toggle at all: the group holding the current page renders open because the server knows the route. One discipline keeps collapsible groups honest: a parent row either navigates or toggles, never both — a row that does two things from one click teaches the reader to trust neither. Nesting stops at one level of children; a third level is a sign the navigation needs restructuring, not deeper indentation. 13. The consequential action

In any list of actions, one choice is usually graver than the rest — delete, archive, remove. The rule: that choice never dresses like its neighbors. It takes the danger color, sits last, and is separated by a divider, so the eye finds it instantly and never hits it by accident. One consequential action per list; anything destructive still asks for confirmation.

14. Dashboards and the size of a number

18. Table editing vs. form editing

Where should a value change: in the table cell, or in the record form the row opens? Products that refuse inline editing are usually not lazy — a form has room for labels, help and errors beside each field, one visible Save, and a shape that approval workflows can review; a grid has none of that by default. Products that embrace inline editing serve a real need: correcting one field across forty rows through a form is miserable. The industry's reconciliation is the draft-plus-save-bar pattern (option B below): edits are held as a draft — changes made on screen but not yet written — tinted cell by cell, counted in a bar with one Save and one Cancel, validated by the server as a batch. That submitted draft is the same object an approval review needs, which is why the pattern fits governed data.

Where should a value change: in the table itself, or in the record form the row opens? Every serious product picks a spot on this spectrum. The options below are the complete catalog, from safest to most fluid; they are not mutually exclusive — a real screen usually combines two or three.

Option A — read-only table, form editing (the default)

The table is for finding and comparing; clicking a row opens the record form, and every change happens there. This is the safest option: the form has room for labels, help text, and error messages next to each field, and one clear Save button. It is the right default for records with many fields or fields that depend on each other.

23. Keyboard conventions — what Enter means

Enter is the most overloaded key in modern software, and chat applications made it worse by teaching millions that Enter sends. The rule that removes the guessing: the kind of control decides what Enter means, identically on every screen — activate in menus, submit in single-line fields (a behavior called implicit submission, built into the web platform), and always a new line in multi-line text boxes, where a surprise submit of a half-written record is the expensive failure. Cmd/Ctrl+Enter is the one universal save-from-anywhere accelerator, taught in place: focus the text box below and the Save button reveals its hint.

Enter is the most overloaded key in modern software: in one product it sends, in another it makes a new line, in a third it activates a menu item — and every user carries each habit into the next application, where it misfires. The rule here removes the guessing: the kind of control decides what Enter means, identically on every screen, never the application's mood.

Choice surfaces — Enter activates the highlighted item

In menus, lists, and palettes there is exactly one sensible thing for Enter to do: pick what is highlighted. Esc closes. The oldest meaning, and the least disputed.

Single-line field — Enter submits the form

Implicit submission is built into the web platform itself; it is why Enter works in every search and login box ever made. It is kept, never suppressed — pressing Enter here is the same as clicking the button.

Multi-line text box — Enter makes a new line, ⌘↵ saves

A text box that accepts paragraphs is a writing surface; in a record system it holds notes and descriptions, not chat messages. The failure modes are not symmetric — a surprise submit fires a half-written record, a newline that did not submit costs one keystroke — so the safe meaning wins: Enter writes, Cmd/Ctrl+Enter saves from anywhere in the form. Click into the text box below and watch the Save button teach the shortcut. Shift+Enter is accepted as a harmless newline synonym for chat-trained hands.

Grid cells — the editing grammar

A grid cell is a different control again, so Enter means something different there — and means it consistently (see the table-editing section above).

↵ / F2 edit the focused cell Esc cancel, restore the old value Tab commit and advance ←→↑↓ travel the grid

Recommendation as stated above; Shift+Enter tolerated as a harmless newline synonym. The one place Enter-to-send would ever be correct is a true chat surface, which does not exist in the system today.

26. Brand color vs. the meaning colors

Red means danger and green means success inside an interface — those meanings are load-bearing. A product whose brand color is red or green therefore has a conflict: if the brand hue also paints buttons and links, every error banner and success badge competes with it. The research recommends role separation (the brand hue owns identity moments — logo, marketing, accent details — while interface semantics keep their own reserved hues) and hue distancing (shifting the interface's semantic red or green far enough from the brand hue that the two never read as the same color).

Recommendation: role separation plus hue distancing, applied per brand skin. Full evidence in the brand-color research file pending its graduation into this chapter.
